# crmai — ИИ-анализ диалогов: Wazzup → LLM → amoCRM

Второй сервис репозитория. Читает переписку менеджера с партнёрами-блогерами
(Telegram/WhatsApp через виджет Wazzup), раз в день формирует статус по каждой
сделке и кладёт его примечанием в amoCRM, проверяет исходящие по чек-листу
компании и шлёт руководителю дайджест. Грубые нарушения — алерт сразу, не
дожидаясь вечернего батча.

**Сервис строго read-only по отношению к перепискам.** Он никогда не
отправляет сообщения партнёрам: только читает, анализирует и пишет в amo
примечания и задачи.

Парсер каналов для хантинга живёт в том же репозитории отдельно — см.
[README.md](README.md).

## Что делает

**Уровень 1 — авто-статусы.** По каждому диалогу с новой активностью собирает
контекст (прошлый статус + свежие сообщения), просит модель вернуть строгий
JSON и пишет в сделку примечание:

```
🤖 Статус на 21.09.2026
Этап: переговоры об условиях | Температура: hot
Партнёр заинтересован, спросил про оплату. Сумма фикса названа без согласования.
Зафиксировано: созвон 22.09
Ждём: реакция партнёра на условия
След. шаг: согласовать фикс и вернуться с оффером (до 2026-09-22)
Риск: названа сумма без согласования
```

Если следующего шага нет или его дата в прошлом — в amo создаётся задача
«Определить следующий шаг по [партнёр]» на завтра 12:00 на ответственного из
`AMO_MANAGER_USER_ID`.

**Уровень 2 — контроль качества.** Проверяет исходящие менеджера за день по
чек-листу (критичные / важные / мелкие) и собирает дайджест руководителю в
Telegram. Критичное нарушение, которое не поймал regex-слой, уходит отдельным
алертом сразу после батча.

**Мгновенные алерты.** Каждое исходящее сообщение проверяется стоп-паттернами
прямо при приёме вебхука — без LLM и без задержки.

## Быстрый старт

```bash
git clone <repo> && cd veles-11
python3.11 -m venv .venv && source .venv/bin/activate
pip install -r requirements-crmai.txt

cp .env.example .env     # заполнить блок «ИИ-анализ диалогов»
python -m crmai config-check

# потрогать конвейер целиком без ключей и без сети
python -m crmai demo

# боевой запуск: вебхук + расписание батчей
python -m crmai serve
```

Дальше в личном кабинете Wazzup подписаться на события `messages` и указать
адрес `https://<домен>/webhook/wazzup` (нужен HTTPS — см.
[deploy/install-crmai.md](deploy/install-crmai.md)).

## Команды

| Команда | Что делает |
| --- | --- |
| `serve` | вебхук Wazzup + расписание батчей. `--no-scheduler` — только вебхук |
| `run-status` | батч уровня 1. `--dry-run` — не писать в amo, `--since` — ограничить период |
| `run-quality` | батч уровня 2. `--date YYYY-MM-DD`, `--no-alerts` |
| `digest` | собрать дайджест за день. `--date`, `--send` |
| `ingest file.json` | обработать тело вебхука из файла (`-` — stdin) |
| `check "текст"` | прогнать текст через regex-слой стоп-паттернов |
| `rules` | показать все стоп-паттерны |
| `amo-check` | проверить доступ к amo, `--lead-id N` — записать тестовое примечание |
| `stats` | сводка базы |
| `config-check` | чего не хватает в `.env` |
| `demo` | весь конвейер на встроенных данных, без сети |

Общие флаги: `--env`, `--db`, `--prompts`, `-v` (подробный лог).

### Примеры

```bash
# Проверить формулировку до отправки
python -m crmai check "по рефке отдаём 40%, доход гарантирован"

# Прогнать вчерашний день заново и отправить дайджест
python -m crmai run-quality --date 2026-09-20
python -m crmai digest --date 2026-09-20 --send

# Проверить приём вебхука на реальном событии из лога Wazzup
python -m crmai ingest event.json
```

## Как это работает

```
Wazzup ──webhook──> FastAPI /webhook/wazzup ──> SQLite (messages, chats)
                              │                      │
                              ├─ regex-слой ─> 🚨 Telegram (сразу)
                              │
   APScheduler, будни:        ▼
   19:00  уровень 1 ─> LLM (П1) ─> примечание + задача в amoCRM
   19:30  уровень 2 ─> LLM (П2) ─> замечания + алерт по критичным
   19:45  дайджест   ─────────────────────────> Telegram руководителю
```

Вебхук отвечает `200` сразу после чтения тела, обработка уходит в фон — Wazzup
не успевает начать ретраи. Дедуп по `messageId`: повторная доставка того же
события не создаёт ни второй записи, ни второго алерта.

Структура пакета:

| Модуль | Ответственность |
| --- | --- |
| `wazzup.py` | разбор события вебхука в нормализованное сообщение |
| `intake.py` | сохранение + мгновенные алерты |
| `redflags.py` | стоп-паттерны без LLM |
| `analysis.py` | уровень 1: статусы сделок, примечания, задачи |
| `quality.py` | уровень 2: чек-лист исходящих |
| `digest.py` | дайджест руководителю |
| `amo.py` / `matching.py` | клиент amoCRM и поиск сделки по чату |
| `llm.py` | Anthropic Messages API, бюджет вызовов, разбор JSON |
| `prompts.py` | шаблоны промптов и сборка диалога |
| `db.py` | SQLite-хранилище |
| `scheduler.py` / `webhook.py` / `cli.py` | расписание, HTTP, командная строка |

## Промпты и контекст компании

Промпты лежат текстом в `prompts/` и правятся без похода в код:

| Файл | Назначение |
| --- | --- |
| `p1_status_system.md` | системный промпт уровня 1 (статус сделки) |
| `p1_status_user.md` | шаблон юзер-промпта: `{prev_summary}`, `{dialog}` |
| `p2_quality_system.md` | системный промпт уровня 2 (чек-лист) |
| `p2_quality_user.md` | шаблон юзер-промпта: `{date}`, `{dialogs}` |
| `company_context.md` | контекст компании — его наполняет владелец системы |

Содержимое `company_context.md` подставляется **в конец обоих системных
промптов**. Туда идут выдержки из внутренней памятки: красные линии, что
только через руководителя, частые возражения и рекомендованные ответы.
HTML-комментарии из файла вырезаются — в них удобно держать инструкции для
себя, модель их не увидит.

Файл читается при каждом батче: правку подхватит ближайший запуск, рестарт
сервиса не нужен.

Диалог приходит модели в формате из ТЗ, свежие сообщения последними:

```
[21.09 09:10] IN: Привет! Сколько платите за интеграцию?
[21.09 09:40] OUT: Смотрел твой разбор по сеточным ботам...
[21.09 09:41] OUT: [media] audio
```

Голосовые и файлы не расшифровываются (вне скоупа MVP): сохраняется факт
сообщения с пометкой `[media]`, и промпт просит модель отметить, если ключевые
договорённости могли быть именно там.

## Стоп-паттерны

Regex-слой из раздела 4.2 ТЗ. Проверяются **только исходящие**: вопрос
партнёра «а доход гарантируете?» нарушением не считается.

| Правило | Ловит |
| --- | --- |
| `guaranteed_income` | `гарантир*` рядом с `доход / прибыл / процент / %` |
| `sure_earnings` | «точно заработаешь», «точно будешь зарабатывать» |
| `no_risk` | «без рисков», «без всяких рисков» |
| `passive_income` | «пассивный доход» |
| `ref_rate` | `35/40/45/50%` рядом с `рефк / ставк / отчислен` |
| `payment_split` | `50/50`, «пополам» рядом с `оплат / плат` |
| `fix_amount` | сумма рядом со словом «фикс» — в алерт с пометкой «проверь, согласована ли сумма» |
| `branded_bot` | «брендированный бот», «персональный бот» |
| `pressure` | «верни деньги», «пойду к», «у нас связи», «юрист», «суд» |

«Рядом» — в пределах примерно одного предложения (80 символов), поэтому
«40% зрителей досматривают ролик» в одном абзаце и «ставка» в другом алерт не
поднимают. Полный список с регулярками: `python -m crmai rules`.

Алерт дедуплицируется по паре (сообщение, правило): повторная доставка события
Wazzup не разбудит руководителя второй раз.

## Матчинг чата на сделку

1. Если amo-идентификаторы пришли прямо в событии Wazzup — берём их (Wazzup сам
   заводит и связывает контакты в amo).
2. Иначе ищем контакт по username, затем по телефону, затем по имени.
3. У контакта берём **открытые** сделки в воронках из `PIPELINE_IDS`; если их
   несколько — последнюю по `updated_at`.
4. Сделки нет — чат помечается `unmatched`, попадает в дайджест строкой
   «Без сделки в amo: N», батч продолжается.

Результат кэшируется в таблице `chats` на сутки, потом ищется заново.

## Надёжность и лимиты

* **Ретраи** к amo, LLM и Telegram: 3 попытки с задержкой 2с → 4с. Финальный
  провал — запись в `failures`, строка в дайджесте, батч живёт дальше.
* **Бюджет LLM**: не больше `MAX_LLM_CALLS_PER_DAY` вызовов в сутки (по
  умолчанию 200). Счётчик в базе, при исчерпании батч останавливается и
  сообщает об этом.
* **Токены amo** обновляются автоматически при 401; новая пара сразу пишется в
  `AMO_TOKEN_FILE` — refresh-токен одноразовый, потеря пары ломает интеграцию.
* **Логи**: на уровне INFO — только идентификаторы и счётчики, без текстов
  переписки. Тексты видны только в DEBUG (`-v`), локально.
* **Ошибка одной сделки не валит батч**: не записалось примечание — падает
  только этот чат.

## Конфигурация

Все ключи и ID — из `.env`, список с комментариями в `.env.example` (блок
«ИИ-анализ диалогов»). Минимум для боевого запуска показывает
`python -m crmai config-check`.

Про `LLM_MODEL`: в ТЗ указана `claude-sonnet-4-6`, она и стоит по умолчанию.
Текущее поколение — `claude-sonnet-5`: дешевле по токенам и сильнее; переход
делается одной строкой в `.env`, код от версии модели не зависит.

## Разработка

```bash
pip install -r requirements-crmai.txt pytest
python -m pytest tests -q
```

Тесты анализатора лежат в `tests/test_crm_*.py` и сети не требуют: HTTP-клиенты
amo и Telegram подменяются фейками, LLM — заглушкой `StubLLM` с заранее
заданными ответами. Тесты вебхука пропускаются, если не установлен FastAPI.

Как добавить стоп-паттерн: дописать `Rule(...)` в `crmai/redflags.py` (при
необходимости с `near=` для проверки «рядом») и случай в
`tests/test_crm_redflags.py`.

Как изменить формат примечания: `build_note()` в `crmai/analysis.py` —
формат зафиксирован тестом `test_note_format_matches_spec`.

### Вне скоупа MVP

Отправка сообщений в чаты; расшифровка голосовых; анализ чатов вне виджета
Wazzup; правка полей сделки, кроме примечаний и задач; веб-интерфейс.
